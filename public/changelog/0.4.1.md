## 0.4.1 — 9 октября 2026

### Связь с сервером
- Если сервер недоступен, приложение больше не отправляет вас на страницу входа и не сбрасывает вход. Вверху появляется сообщение «Нет связи с сервером. Вход сохранён, переподключаемся.» с кнопкой «Повторить», а когда связь вернётся, оно исчезает само.
- Если сервер недоступен при открытии приложения, показывается страница ожидания, а как только связь появляется, вы попадаете на ту страницу, которую открывали.
- Вход сбрасывается только тогда, когда сервер явно отклонил сессию. Обрыв связи, ошибка шлюза или ошибка сервера при проверке входа его не отменяют: в последнем случае страница предложит повторить попытку.
- Нестабильное соединение больше не принимается за отсутствие связи. Сообщение появляется, только когда подряд не ответили несколько проверок, а единичный оборванный запрос или сбой одного обработчика его не вызывает.
- Приложение различает технические работы и сбой: вместо общего «Нет связи с сервером» оно показывает «Проводятся технические работы» или «Сервер недоступен по техническим причинам, обратитесь в поддержку». Страницы Traefik принимаются как прямой ответ инфраструктуры, поэтому ждать повторных проверок не нужно, а когда причина меняется, текст обновляется сам.
- Обновление входа выполняется одним запросом за раз: сервер отзывает всю сессию, если один и тот же токен обновления предъявить дважды.

### Развёртывание и технические работы
- Способ развёртывания выбирается глобально: монолит или микросервисы. Режим задаётся переменной COMPOSE_PROFILES (monolith или microservices) в .env либо флагом --mode у скрипта scripts/deploy.sh. Одновременно работает один режим, при переключении контейнеры другого режима удаляются, а бот работает отдельным контейнером в обоих режимах.
- В режиме микросервисов сервисы всегда обмениваются сообщениями через Kafka (IN_MEMORY_BROKER=false), потому что отдельные процессы не могут делить брокер в памяти. Сервис mail теперь тоже ждёт готовности Kafka.
- Скрипт scripts/deploy.sh обновляет всё одной командой: собирает образы, пока работает старая версия, включает режим технических работ, обновляет контейнеры, дожидается их готовности и снимает режим. Ошибка сборки ничего не меняет, а если обновление не удалось, режим работ остаётся включённым и скрипт подсказывает, как его снять. Вручную режим управляется командами scripts/deploy.sh maintenance on, off и status.
- Во время технических работ API отвечает кодом 503 со страницей «Проводятся технические работы» (HTML для браузера, JSON для приложения) и заголовком Retry-After. Сайт приложения при этом остаётся доступен.
- Когда сервис недоступен по технической причине, Traefik сам показывает страницу «Сервер недоступен по техническим причинам, обратитесь в поддержку или к администрации». Это работает и для остановленного контейнера, и для запущенного, но не отвечающего на проверку.
- Traefik проверяет здоровье сервисов сам, каждые 3 секунды, и не ждёт проверки Docker, которая обнаруживала сбой до 75 секунд.
- Собственные ответы сервисов с кодом 503, например «push-уведомления не настроены», страницей недоступности не подменяются.
- Запасного перехода на монолит больше нет: если у сервиса нет здорового контейнера, его запросы получают страницу недоступности, а не обрабатываются монолитом.
- Страницы недоступности и работ отдают заголовки CORS для известных адресов приложения, поэтому браузер может прочитать причину.

### Сервер и API
- Каждый сервис (user, event, org, profile, geo, notify, bot и mail) отдаёт проверку живости GET /сервис/v1/health: состояние, имя сервиса и версию. Она описана в схемах v1 и есть в клиенте фронтенда.
- Контейнеры в docker-compose проверяются по этим адресам, а контейнер aef — по /user/v1/health.
- У сервиса mail появился HTTP-интерфейс v1: пока в нём только проверка живости.
